# 서비스 정의와 실제 구현 설계

이 페이지는 이 프로젝트가 제안하는 서비스를 **실제 현장에 구현한다고 가정**하고, 요소마다 지금 시뮬레이션에서 무엇으로 대신했는지와 실제로는 무엇이 필요한지를 정리합니다.

:::{important}
아래 '실제 구현' 칸은 **설계 가정**입니다. 실물 로봇에서 시험한 것은 하나도 없습니다. 시험한 것은 Gazebo Sim 에서 돌린 것뿐입니다 ({doc}`../results/test_results`).
:::

## 1. 어떤 서비스인가

**재난 현장 생존자 탐색.** 구조 지휘자가 임무를 요청하면 바퀴 로봇 한 대(Husky)와 사족 로봇 두 대(A1)가 도로를 따라 건물을 차례로 돌며 안을 탐색하고, 찾은 생존자의 위치를 알려 줍니다. 사람이 들어가기 전에 **어느 건물 어디에 사람이 있는지**를 먼저 아는 것이 목적입니다.

| 항목 | 내용 |
| --- | --- |
| 사용자 | 구조 지휘 요원 (현장 밖에서 노트북으로 요청·감시) |
| 입력 | 현장 설정: 건물 세트별 Husky 주차점, 로봇별 탐색 구역, 예상 인원 (`mission.yaml`) |
| 요청 | 임무 시작·취소, 통신 끊김 시험, 생존자 조회 ({doc}`../reference/interfaces`) |
| 출력 | 생존자 위치 목록 (출발점 기준 좌표, m), 진행 단계, 로봇별 지도 |
| 역할 분담 | Husky = 운반·지휘·집계, A1 = 건물 안 탐색·사람 찾기 |

## 2. 운용 절차

| 순서 | 운용자가 하는 일 | 시스템이 하는 일 |
| --- | --- | --- |
| 1. 현장 설정 | 평면 정보로 주차점·구역·예상 인원을 `mission.yaml` 에 적음 | — |
| 2. 로봇 배치 | Husky 를 기준점에 두고 A1 두 대를 뒤 1.6 m, 좌우 0.8 m 에 같은 방향으로 세움 | — |
| 3. 기동 | 시스템을 띄움 | `husky_mission` 이 `IDLE` 에서 대기 |
| 4. 임무 요청 | `RunMission` 목표 (`num_sets`) | 세트마다 이동 → 탐색 → 복귀 |
| 5. 감시 | 피드백(단계·찾은 수)을 보고, 필요하면 `GetSurvivors` 로 위치 확인 | 사람을 찾으면 1 초 서고 보고 |
| 6. 결과 | 액션 결과의 생존자 목록을 받음 | `DONE` |
| 7. 판단 | **위치를 확인해 중복·누락을 가려냄** (아래 5 절) | — |

중간에 멈추려면 액션을 취소합니다. A1 한 대를 직접 몰아야 하면 `/<ns>/cmd_vel_teleop` 이 모든 자동 명령보다 우선합니다 ({doc}`../how_to/teleop`).

지금은 시뮬레이션에서 이 절차를 `run_mission.sh` 하나가 3~4 단계를 대신합니다 ({doc}`../getting_started/quickstart`).

## 3. 요소별 구현

### 하드웨어

| 요소 | 시뮬레이션에서 | 실제 구현 가정 |
| --- | --- | --- |
| 운반·지휘 로봇 | Husky A200 모델 (Gazebo DiffDrive), 2D 라이다·IMU | 실물 A200 + 같은 센서. `/husky/cmd_vel` 을 구동기에 연결 |
| 탐색 로봇 | Unitree A1 모델 2 대, CHAMP 보행 | 실물 A1. 보행 설정(`gait.yaml`)은 시뮬레이션에서 맞춘 값이라 다시 맞춰야 함 |
| 거리 센서 | 평면 라이다 360°, 10 Hz, 10 m (높이 약 0.30 m) | 같은 사양대의 2D 라이다. 더 낮거나 높은 장애물은 따로 필요 |
| 카메라 | 앞 RGB 640×480, 수평 103°, 2 Hz | RGB 카메라. 어두운 곳은 조명이나 열화상 필요 |
| 깊이 센서 | 지형용 깊이 점구름 5 Hz | 깊이 카메라 |
| 연산 | PC 한 대에서 전부 (시뮬레이션 포함) | 로봇마다 탑재 컴퓨터 (아래 표) |

### 소프트웨어를 어디서 돌리나 (제안)

| 위치 | 노드 | 비고 |
| --- | --- | --- |
| A1 각 대 | 보행 제어, EKF, `scan_ready_relay`, slam_toolbox, Nav2, `terrain_node`, `nav_executor`, `a1_follower`, `return_relay`, `cmd_vel_arbiter`, `survivor_detector` | 통신이 끊겨도 정지·복귀할 수 있어야 하는 것. 지금은 두 로봇을 한 프로세스가 다루는 노드가 많고, `robots` 파라미터로 나눠 띄우는 구성은 시험하지 않음 |
| Husky | `husky_mission`, `husky_driver`, `nav_goal_bridge`, `frontier_detector`, `frontier_comm_filter`, `goal_assigner` | 두 로봇의 지도를 모아 목표를 나누는 쪽 |
| 지휘자 노트북 | `RunMission`·`SetComm`·`GetSurvivors` 호출, 화면 | 전용 화면(UI)은 만들지 않았고 `ros2` 명령줄과 RViz 를 씀 |

### 통신

| 요소 | 시뮬레이션에서 | 실제 구현 가정 |
| --- | --- | --- |
| 연결 | 한 PC 안의 ROS 2 (DDS) | Wi-Fi 또는 메시 무선. 건물 안에서는 중계기가 필요할 수 있음 |
| 끊김 판정 | `/<ns>/comm_status` 하트비트가 벽시계 1 초 없으면 끊김 | 같은 방식을 그대로 쓸 수 있음. 거리·벽에 따른 끊김은 모델에 없고 `SetComm` 으로만 흉내 냄 |
| 끊겼을 때 | A1 은 지나온 길을 되짚어 탐색 시작 위치로, Husky 는 정지. 발견은 모아 두었다가 보냄 | 되짚기는 로봇 자체 odom 만 씀. 모아 보내기는 시뮬레이션에서 1 회(1 건) 확인 |
| 오가는 데이터 | 로봇 지도, 자세, 목표, 단계, 사람 보고 | 지도(`OccupancyGrid`)가 가장 큼. 대역폭은 재지 않음 |
| 보안 | 없음 | 인증·암호화(SROS 2 등) 필요 |

### 위치와 좌표

| 요소 | 시뮬레이션에서 | 실제 구현 가정 |
| --- | --- | --- |
| 좌표 기준 | 출발 자세를 알고 시작 (`mission.yaml` 의 `spawn`) | 출발 대형을 실측해 입력 |
| Husky 위치 | 바퀴 속도 × IMU 방향 | 긴 거리에서는 GNSS 나 지도 정합이 필요 |
| A1 위치 | 로봇별 SLAM + 세트마다 라이다로 본 Husky 기준 보정 | 같은 방식. 보정은 A1 이 Husky 를 볼 수 있어야 함 |
| 결과 좌표 | 출발점 기준 x, y (m) | 실제 지도 좌표(GNSS)로 바꾸는 단계는 만들지 않음 |

### 탐색과 이동

| 요소 | 시뮬레이션에서 | 실제 구현 가정 |
| --- | --- | --- |
| 도로 이동 | 직선 도로를 라이다로 장애물만 피해 주행 | 굽은 길·교차로는 경로 계획이 필요 |
| 건물 탐색 | 프런티어 + Nav2 (오픈소스) | 그대로. 계단, 문 열기, 층 이동은 지원하지 않음 |
| 구역 | 축에 나란한 사각형 | 비스듬한 건물은 다각형 구역이 필요 |
| 지형 | 낮은 턱·8° 둔덕 | 잔해 더미 같은 거친 지형은 시험하지 않음 |

### 생존자 인식

| 요소 | 시뮬레이션에서 | 실제 구현 가정 |
| --- | --- | --- |
| 인식 | YOLOv4-tiny (COCO), 서 있는 마네킹 | **누워 있거나 일부만 보이는 사람은 시험하지 않음.** 재난용 데이터로 다시 학습, 열화상·음성 추가 필요 |
| 거리 | 상자 높이(키 2.0 m 가정) + 라이다 | 서 있는 키를 가정하므로 앉거나 누운 사람에는 맞지 않음. 깊이 카메라로 바꿔야 함 |
| 확인 | 자동 보고 | 지휘자가 영상으로 확인하는 단계가 필요 (영상 전송은 만들지 않음) |

### 안전과 전원

| 요소 | 지금 있는 것 | 실제 구현에 필요한 것 |
| --- | --- | --- |
| 속도 명령 | `cmd_vel_arbiter` 하나만 로봇에 씀, 입력이 끊기면 0 | 하드웨어 비상 정지 |
| 사람 조종 | teleop 이 최우선 | 무선 비상 정지 |
| 넘어짐 | 기울기 45° 넘으면 목표 취소 | 자세 회복, 알림 |
| 충돌 | 라이다 + 비용지도 | **A1 끼리는 서로 거의 못 봄** (아래 5 절). 사람과의 거리 유지 규칙도 필요 |
| 전원 | 모델 없음 | 배터리 감시와 부족 시 복귀. 임무 시간(시뮬 약 15~18 분)을 실물 배터리가 버티는지 확인 필요 |

## 4. 문제가 생기면

| 상황 | 시스템 동작 | 운용자가 할 일 |
| --- | --- | --- |
| 통신 끊김 | A1 복귀, Husky 정지, 복구되면 이어 감 | 중계기 위치 조정 |
| 한 세트 탐색이 1,500 초 초과 | `REGROUP`: A1 을 불러들이고 다음 세트 | 그 세트를 미완료로 기록 |
| 갈 곳이 막힘 | 블랙리스트, 벗어나기, 옮겨 보기. 계속 실패하면 그 방은 포기 | 미발견 인원이 있으면 직접 확인 |
| A1 복귀 실패 (8 번) | 그 자리에서 세트 완료, 다음 이동에서 Husky 가 기다림 | 로봇 회수 또는 조종 |
| 예상 인원보다 적게 찾음 | `미발견 n` 으로 남기고 진행 | 재탐색 여부 판단 |

## 5. 알려진 문제와 실제 배치 전에 할 일

지금 알고 있는 문제 (자세히 {doc}`../results/limitations`):

- **보고 수가 실제 사람 수보다 클 수 있습니다** (전체 실행에서 11 명에 11~13 건). 위치를 보고 판단해야 합니다.
- **A1 끼리 닿을 수 있습니다.** 라이다 평면이 상대의 몸통보다 위입니다.
- **카메라 시야 밖 사람은 놓칩니다.** 탐색 끝은 라이다 지도 기준입니다.
- 좁은 복도에서 길을 닫아 안쪽 방을 포기할 수 있습니다.

실제 배치 전에 만들어야 하는 것:

1. 운용자 화면 (지도, 생존자 위치, 영상 확인, 비상 정지)
2. 로봇별 탑재 실행 구성과 무선 통신 시험
3. 실제 지도 좌표 변환
4. 재난 상황 사람 인식 (누운 사람, 열화상)
5. 배터리 감시와 하드웨어 비상 정지
6. A1 끼리 충돌 회피
